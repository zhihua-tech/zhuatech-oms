## 第一版架构

项目采用前后端分离和模块化单体架构，优先保证个人学习环境中的可理解性、可运行性和订单链完整性。前端通过 REST API 调用后端，Java 根包为 `cn.zhuatech.oms`，MySQL 表统一使用 `oms_` 前缀。

```text
渠道 / 人工建单
       │
       ▼
CustomerOrder ── OrderEvent
       │
       ├── Shipment
       ├── AfterSaleRequest
       └── SalesChannel
```

## 核心聚合

- `CustomerOrder`：统一承载内部订单号、渠道订单号、客户、商品摘要、金额、状态、仓库和承诺时间。
- `Shipment`：描述一次发运任务以及仓库、承运商、运单、包裹状态和预计送达时间。
- `AfterSaleRequest`：描述退款、退货退款或换货申请及处理状态。
- `SalesChannel`：描述订单来源、同步健康度、今日订单量和成交额。
- `OrderEvent`：记录支付、分仓、履约、物流、售后等关键事件。

## 关键约束

1. 内部订单号和售后申请号必须唯一。
2. 订单状态只能使用领域枚举，非法状态由业务异常统一拦截。
3. 每次人工状态变化都生成订单事件，便于审计与时间线展示。
4. 明文密码不入库，密码通过 BCrypt 保存，接口通过 JWT 鉴权。
5. 数据库结构由 Flyway 管理，发布后新增迁移，不修改已执行脚本。

## 生产化建议

真实多渠道 OMS 通常还需要消息队列、幂等表、分布式锁、库存中心、规则引擎、WMS/物流连接器、对账、租户隔离、审计日志和可观测性。第一版仅提供可扩展的学习骨架，不应在未取得商业授权和生产加固的情况下直接承载企业订单。
